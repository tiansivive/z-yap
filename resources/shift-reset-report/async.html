Async, await, fire, and continuation escape

The early problem

Async was explored as an interpretation of shift. await captures the rest of the computation; a scheduler or task runtime resumes it when a result is ready.

await task
≈
shift [Async] (k => register task k)

The surface language can offer direct style without baking async into every layer of the core calculus.

The constraint

Suppose the handler stores or returns k:

shift [Async] (k => {
  queue.push(k)
  return unit
})

The body may appear to finish without Async, but it has not become synchronous. The captured continuation is now scheduled elsewhere. The async capability has moved, not disappeared.

Therefore, a reset handles Async only when the handler contains the continuation’s future behavior. If it hands the continuation to a task queue, returns it, stores it in a closure, or calls an unknown function with it, the surrounding type must preserve the appropriate obligation.

Fire-and-forget

fire is not merely await without a result. It discards the caller’s dependency on the result while still creating work and ownership questions:

  • Who owns the spawned continuation?
  • Can it fail, and where does that failure go?
  • Can it outlive the current reset?
  • Is it cancelled when the parent scope exits?
  • Can it be resumed once or repeatedly?

The existential prompt mechanism can delimit the local control action, but structured concurrency and cancellation semantics still need an explicit design.

Handler stores, returns, or passes k to unknown codeEffect/capability escapes; it must remain represented in the type or capability environment.
