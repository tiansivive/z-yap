# Fuzz testing

Fuzz testing targets three pipeline stages where malformed or adversarial input is most likely to surface crashes, hangs, or unsound behavior.

**Parser fuzzing.** Random and mutated source strings fed through the Nearley parser (and eventually tree-sitter) to discover crashes, ambiguities, and error recovery failures. Grammar-aware fuzzing — generating strings from the grammar with random choices at each production — complements purely random byte mutation. Tree-sitter has built-in fuzz harness support via `tree-sitter parse --debug`.

**Elaboration fuzzing.** Well-formed CSTs generated by parser fuzzing (or a dedicated AST generator) fed into `EB.infer` to find elaboration crashes, infinite loops (step budget), unsound type assignments, or internal invariant violations. The step budget on NbE evaluation already provides a natural termination guard, but fuzz runs would help validate its effectiveness.

**Solver fuzzing.** Random IVL formulas constructed via the `DSL` module fed into `Solver.create()` → `solver.assert()` → `solver.check()` to find CDCL crashes, theory plugin failures, or incorrect sat/unsat results. Differential testing against Z3 (via the `z3-solver` npm package that still exists as a dependency) could serve as an oracle for correctness.

**Tooling.** `fast-check` provides TypeScript-native property-based testing with shrinking. For parser fuzzing, a grammar-derived `Arbitrary` that produces syntactically valid (or near-valid) Yap programs would be the highest-value generator. For the solver, composing IVL `Term` trees via `fast-check` combinators over the `DSL` constructors is straightforward.
